# 问数前的信息检查与追问设计

状态：小主已确认，2026-11-24 开始按设计直接实施。

## 目的与依据

小主要求：数据库缺少相关信息时，明确告诉客户缺少什么；问题不清楚时先追问；指标口径不明确时，禁止模型自行猜测。

当前 QueryService 创建历史记录后直接运行检索、筛选、SQL 生成和校验。只有 result/error 两类终态；generate_sql.prompt 明确允许未覆盖的指标按业务常识处理。表或字段不存在时通常到 EXPLAIN 才失败，而可执行的 SQL 也可能没有回答客户真正的问题。

本次扩展现有 FastAPI、LangGraph 和 React 链路，保持本地 MySQL、嵌入式 Qdrant 与现有模型接口。现有工作区包含尚未提交的后台管理和界面改动，实施时必须保留。

## 方案比较

1. 纯规则：可验证、调用成本低，但难以覆盖自然语言歧义与业务概念。
2. 只增加提示词：改动少，判断依赖模型，缺少程序对元数据和终态的校验。
3. 元数据核验与模型语义评估结合：模型理解问题，程序验证引用的表、字段、指标依据，并在不充分时结束 SQL 链路。需要增加评估节点、回复类型和追问上下文。

采用第三种。这是实施方依据小主提出的行为目标作出的技术选择，尚未视为小主对设计文档的确认。

## 行为约定

- 信息充分：继续现有 SQL 查询流程。
- 缺少信息：返回正常业务回复，说明缺少的业务信息，例如“当前已接入的数据源缺少商品评价或评分信息，无法计算客户满意度”。不能用一个未召回到的字段直接断言整个数据库没有该信息。
- 问题存在实质歧义：提出最多三个具体问题，保留原问题；用户在同一会话补充后重新评估，再决定查询或继续追问。
- 指标口径缺失：说明缺少公式、统计范围、过滤条件或比较基准中实际需要的内容。指标只采用已配置且一致的定义，或用户明确提供的口径。不能凭常识补充口径。
- 简单明细、计数或明确求和可按用户明确的操作执行，不要求每个普通查询都预先注册为业务指标。不能暗中选择“本月”等范围；确有多种解释且会改变结果时追问。
- 定义与字段依赖不一致：要求确认或修正定义。例如目前 AOV 描述平均订单金额却只关联 order_quantity，新流程应指出该定义存在矛盾，不能替用户决定正确公式。
- SQL 返回零行：仍然正常显示“没有符合条件的数据”，与缺少表/字段、指标不明确分别处理。
- 评估模型异常或输出不合约：作为技术错误返回，不绕过检查生成 SQL，也不把故障误报成数据库缺少业务信息。

## 后端流程

1. 接收原问题或针对既有追问的补充，创建本次历史记录。
2. 读取已接入数据源的完整表、字段和指标目录，并核对实际 dw 表结构。目录来自可信元数据，不以向量检索命中率代表数据是否存在。
3. 新增查询评估节点，给模型提供问题、已验证目录、指标定义及必要的追问上下文。
4. 使用结构化且严格校验的评估输出，包含状态、面向客户的说明、缺失信息、追问、所需字段与指标依据。所引用字段和指标必须属于真实目录；指标定义缺失或相互矛盾不能进入可查询状态。
5. 对可查询的问题运行现有召回、合并和筛选。保留已确认的必要字段及指标依据，避免后续筛选丢失。SQL 提示词仅使用已确认口径，移除“按通用业务常识进行”条款；修正 SQL 也遵守同一约束。
6. SQL 的表和字段仍受真实目录约束，现有只读 AST、EXPLAIN、修正次数、行数和超时限制继续生效。
7. 需要补充或无法回答时直接结束，不生成、不校验、不执行 SQL。回复通过新增业务 SSE 事件返回；QueryService 将其视为有效终态，而不是“流程结束但没有结果”的错误。

这是一项基于元数据约束的改进，不宣称语义模型绝对不会判断错误。采取严格输出校验、缺乏依据时停止及实际业务用例测试降低误答风险。

## 追问、接口与历史

- POST /api/query 保持 query 字段，增加可选 parent_history_id。旧的仅提交 query 的请求仍可使用。
- parent_history_id 指向后端保存的待补充记录。后端验证记录存在、状态和上下文有效，读取可信历史，不接收客户端伪造的“已批准查询计划”。
- 原问题、系统追问和用户补充始终保留。单次问题保持当前长度限制，追问链限制长度，避免无限上下文增长。
- 增加统一的业务回复 SSE 事件，区分 clarify 和 unsupported。ready 继续现有 result；运行故障保持 error。
- 历史状态增加 clarify、unsupported，均在现有 String(16) 范围内。增加一列可空 JSON 回复字段，用于保存业务说明、追问和续问上下文；正常结果继续存 result，不能把追问伪装成结果表格。
- ORM、历史实体、API、后台查询筛选同步支持新状态。启动时复用现有可空列补齐迁移；旧历史记录保持可读。无需删除或重建已有表。

## 客户界面

沿用当前消息卡片和输入框，新增“需要补充信息”和“当前数据不足”两种回复表现，正常展示客户能理解的原因与问题，不渲染失败 SQL 或假结果表格。

示例：

> 客户：看看最近销售情况。
>
> 助手：请补充你要查看的时间范围，以及关注销售额还是销量。
>
> 客户：本月的销售额，按地区汇总。
>
> 助手：针对原问题和补充重新检查，通过后执行查询。

追问出现后，下一次发送自动携带该记录的上下文。新建分析会清除待补充状态；打开待补充历史可恢复原问题及追问，避免补充回答被当成独立问题或串入其他会话。普通 SQL 查询仍提供进度、图表、表格、SQL 和 CSV。

## 范围与非目标

本次包含评估、受约束 SQL 生成、业务回复、连续追问、历史恢复以及相关验证。不引入新模型供应商、登录系统、远程数据库、知识库自动抓取或通用客服聊天；不自动创建客户缺少的数据、不擅自改动已有业务指标定义。

## 验收与验证

- 缺少评价/评分数据的满意度问题：清楚说明缺少评价信息，SQL 生成和执行次数均为零。
- “最近销售怎么样”等含糊问题：返回具体追问；补充时间、指标和分组后沿原问题继续。
- 未定义复购率或口径不完整的利润率：询问真正缺少的公式/范围，不自行采用常见算法。
- AOV 定义与依赖字段不一致：停止并说明需确认，避免选择一个可执行但错误的计算。
- 明确且有依据的销售额汇总：继续原有正常链路；检索遗漏已知字段不能误报数据源缺失。
- 真实零行结果：仍然完成，不误报 unsupported。
- 模型输出未知字段、未定义指标、无效 JSON 或发生异常：不能绕过检查。
- 业务回复能够保存、打开、续问；新建会话和切换历史不能串上下文。
- 旧 API、历史记录、SQL 只读验证、取消和超时行为不回归。

验证采用有针对性的单元和整图测试、历史/API 测试、前端类型检查与构建，以及实际页面的追问和续问流程检查。必要时重启本次已启动的后端以应用新代码和可空列迁移，再检查前端代理与真实业务用例。
