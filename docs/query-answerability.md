# 问数前的信息检查与追问

完整 API 模式会在检索和 SQL 生成之前，核对已接入的元数据目录与实际数据库字段，然后评估问题是否清楚、数据是否足够、指标是否有明确依据。

- 数据不足：说明具体缺少的业务信息，停止 SQL 链路。例如数据源没有评价或评分时，不能用订单金额、会员等级代替客户满意度。
- 需要补充：提出最多三个具体问题，用户在同一会话回答后沿原问题重新检查。未知复购率、ROI 等指标会要求给出公式及必要范围。
- 定义矛盾：要求确认指标定义及依赖字段。例如当前 AOV 说明平均订单金额，却关联订单数量，不能据此计算。
- 已确认：使用真实字段及已配置且一致的定义，或用户明确给出的计算说明；不允许按业务常识补充指标口径。

单纯重复指标名称、说“复购率平均值”或提供定义链接，不算提供了完整计算说明。客户端提供的系统追问文字也不能作为用户确认公式的证据。

当前日期由服务端提供，明确的“本月”“本季度”“最近 N 天”按该日期处理；只说“最近”时仍需补充范围。评估只使用元数据说明，不把字段样例当成整个数据源的记录覆盖范围。

## 前端使用

页面分别显示“需要补充信息”和“当前数据不足”。收到追问后，下方输入框显示“提交补充”；新建分析或切换到其他历史会清除原来的待补充关联。打开待补充历史会重新加载完整回复并恢复续问。

补充最多 5 轮，每次输入仍限制为 500 字。达到上限、父记录已删除或状态不匹配时，会提示新建分析并写明完整问题。

查询返回零行仍显示“没有符合条件的数据”，不会被当成缺少表或字段。技术故障保持错误状态，不会绕过评估执行 SQL。

## API 与历史

普通请求保持 `POST /api/query` 和 `{"query":"问题"}`。针对待补充记录的回答可增加 `parent_history_id`：

```json
{
  "query": "2025 年第一季度的销售额，按地区汇总",
  "parent_history_id": "待补充记录的 UUID"
}
```

后端验证父记录并读取已保存的原问题和补充；客户端不能提交已批准的查询计划。

SSE 新增终态事件：

```json
{
  "type": "assessment",
  "history_id": "当前记录的 UUID",
  "status": "clarify",
  "reason": "ambiguous_query",
  "message": "请补充时间范围和分析指标。",
  "questions": ["查看哪个时间范围？", "关注销售额还是销量？"],
  "missing_information": []
}
```

数据不足使用 `status=unsupported`、`reason=missing_data`；缺口径与定义矛盾分别使用 `undefined_metric` 和 `inconsistent_metric`，状态为 `clarify`。正常结果和运行错误继续使用原来的 `result`、`error` 事件。

`meta.query_history` 新增可空 JSON `response` 列，保存业务回复和追问上下文。后端启动时补齐旧表列，旧结果和 SQL 保留；历史摘要列表仍不加载完整结果、SQL 或业务回复，打开详情才读取。前端与后端需一起升级以识别新事件和状态。

复杂语义仍由模型评估，检查不构成业务答案绝对正确的保证。无法确认依据或模型输出不合约时，系统会停止本次查询；正式业务指标应维护明确、一致的定义与字段依赖。
